# C3 보고서 내용 규격 설계

이 문서는 2026-10-04에 썼다. 상위 설계는 `docs/superpowers/specs/2026-10-04-report-quality-architecture-design.md`이고, 측정 도구(C0 하네스) 설계는 `docs/superpowers/specs/2026-10-04-c0-eval-harness-design.md`, 페이지 틀 설계는 `docs/superpowers/specs/2026-10-04-c2-page-frame-design.md`다.

## 목적과 범위

C3는 보고서 작성 규칙과 내용 검사를 고쳐, 마무리 보고서를 받은 사용자가 다시 묻지 않고 결정하게 한다. 상위 설계와 이 문서가 다르면 상위 설계를 따르고, 다르게 정한 점은 리포트에 적는다.

이 문서가 쓰는 이름은 다음과 같다.

- **L1:** 메인 세션이다. 공식 측정과 병합을 맡는다.
- **L2:** C3를 맡는 서브오케스트레이터다. 이 문서의 독자이고, 사용자와 대화하지 못한다.
- **BLOCKED:** L2가 L1이나 사용자의 결정이 필요할 때 작업을 멈추고 질문과 함께 돌려주는 상태다.
- **C0 하네스:** 다른 컴포넌트를 판정하는 측정 도구다(`eval/gates.py`, `eval/shoot.py`, `eval/checklist.md`).
- **C2:** 페이지 틀·CSS 컴포넌트다. 이 문서가 쓰는 클래스(`.sec`, `td.chg`, `span.state`, `div.superseded`)의 화면과 결론 제목 검사를 만든다. C3와 동시에 개발되며, C3보다 먼저 병합된다.
- **마무리 보고서:** 작업을 끝낸 뒤 결과, 남은 일, 사용자가 정할 사항을 알리는 보고서다.
- **새 규약 문서:** 절 이름(`p.sec`)을 쓰거나 마무리 보고서 표시(`<main data-kind="wrapup">`)가 있는 문서다. 이 문서의 새 검사는 새 규약 문서에만 적용한다. 그래서 기존 문서와 고정 견본은 새 검사로 위반이 생기지 않는다.
- **재생성 원자료:** L1이 보관하는 원자료다. L1은 이 원자료로 새 스킬과 옛 스킬이 각각 만든 보고서를 비교한다. 상위 설계의 '고정 원자료'와 같은 대상이다.

소유 파일은 다음과 같다. 그 밖의 파일은 읽기만 하고, 고쳐야 하면 BLOCKED로 돌려준다.

- **규칙 문서:** `SKILL.md`, `마무리-보고서.md`(새로 만든다)
- **검사와 시험:** `checks/content.py`, `tests/test_content.py`
- **견본:** `examples/**`(새로 만든다)
- **작업 기록:** `docs/superpowers/plans/2026-10-04-c3-content-rules.md`와 그 리뷰 기록

## 규칙 문서의 배치

마무리 보고서에만 쓰는 규칙은 새 파일 `마무리-보고서.md`에 두고, `SKILL.md`에는 판별 기준과 그 파일을 가리키는 문장만 둔다. 모든 보고서 작업이 항상 읽는 SKILL.md가 비대해지면 기존 규칙과 새 규칙이 겹쳐 모델이 어느 쪽을 따를지 흐려지기 때문이다. 시각화 규칙을 `시각화.md`로 뺀 사전 정리와 같은 방식이다.

SKILL.md의 「작업 방식」 표에는 '마무리 보고서' 행을 추가한다. 판별 기준은 이렇다. 작업을 끝내고 결과·남은 일·결정 사항을 알리는 보고서이면 마무리 보고서로 보고, `마무리-보고서.md`를 따른다. SKILL.md에서 시각화·애니메이션·스타일 규칙은 `시각화.md`와 `보고서-규격.md`를 가리키는 문장만 둔다.

## 마무리 보고서의 필수 절

마무리 보고서는 아래 다섯 절을 두고, 각 절은 `<section data-part="…">` 속성으로 식별한다. 해당 사항이 없는 절은 '해당 없음' 한 줄로 끝낸다. 사용자가 보고서를 받은 뒤 따로 물었던 질문(무엇이 바뀌었나, 남은 것이 있나, 미룬 보강을 진행하라)에 미리 답하고, 정할 사항을 한곳에 모으기 위해서다.

| 절 이름 | `data-part` | 내용 |
|---|---|---|
| 바뀐 것 | `changed` | 변경 전후 표와 바뀐 칸 표시(`td.chg`) |
| 처음 요청 대비 달성 | `achieved` | 처음 요청한 항목마다 달성·일부 달성·미달성과 그 근거 |
| 남은 일 | `remaining` | 항목마다 처분(지금 함·미룸·하지 않음), 권장안, 예정 시점 |
| 결정 요청 | `decisions` | 정할 사항마다 선택지, 권장안과 그 이유, 기각한 대안과 이유. 이미 정한 사항도 이 절에 '결정한 사항'으로 기각한 대안과 함께 둔다 |
| 검증 범위 | `verification` | 실행으로 확인한 사항(명령과 출력)과 확인하지 않은 사항 |

결정 요청 절의 형식은 결정 메모와 결정 기록(ADR) 관행을 따른다(`docs/superpowers/research/2026-10-04-report-quality/lens-prior-art-B.md`).

## 작업 과정의 변경

마무리 보고서를 새로 만들 때 아래 규칙을 따른다. 기존 HTML을 고치는 작업에서는 이 규칙을 적용하지 않고, 해당하는 결함을 보고로만 알린다. 수정 작업은 본문 문장과 숫자를 바꾸지 않는다는 기존 규칙 때문이다.

- **결정 먼저:** 2단계(파일 내용 정리)의 요약 결론 확인에서 미결정 사항이 나오면, 보고서를 쓰기 전에 하나씩 결정받는다. 사용자에게 물을 수 없는 실행자(서브에이전트)는 미결정 사항을 결정 요청 절에 그대로 둔다.
- **원본 기준 표시:** 보고서 머리에 `<p class="basis">`로 보고서의 기준을 적는다. 기준은 커밋, spec 경로, 원자료 파일 경로 가운데 하나 이상이다.
- **대체됨 배너:** 새 보고서가 옛 보고서를 대체하면, 새 보고서를 만드는 세션이 옛 보고서 머리에 `<div class="superseded"><b>대체됨</b> 새 문서 경로와 바뀐 이유</div>`를 단다.
- **질문과 용어 먼저:** 파일 첫머리에 그 파일이 답하는 독자의 질문을 보이고, 핵심 용어는 처음 쓰기 전(애니메이션은 재생 전)에 풀이한다.
- **시각 검토 단계:** SKILL.md 완료 기준의 헤드리스 Edge 스크린샷 단계를 C0 하네스로 바꾼다. 기계 판정(`eval/gates.py`)을 실행하고, `eval/shoot.py` 출력과 `eval/checklist.md`만 받은 검토 서브에이전트로 체크리스트를 확인한다.
- **원격 게시:** 원격에서 열 수 있게 게시하기 전에 민감 정보(사내 이름, 경로, 수치의 공개 여부)를 먼저 점검한다. 그다음 점검 결과를 보이며 사용자 확인을 받고, 확인을 받은 뒤에 게시한다.

## 페이지 구성과 제목 체계

페이지형 보고서의 결론 페이지는 절 이름(`p.sec`), 결론 제목(`h2`), 결론 불릿, 근거, 중요 포인트, 유의사항, 출처의 순서로 쓴다. 결론이 없는 페이지는 절 이름 없이 명사구 `h2`만 둔다. 결론이 없는 페이지란 요약, 그리고 절차·목록·부록처럼 `class="page list"`로 표시한 페이지다. 이 체계는 사용자 원칙 `TITLE-LAYERS`와 2026-09-27 사용자 지시를 함께 따른다. `TITLE-LAYERS`는 한 페이지씩 넘겨 보는 HTML의 페이지 제목을 결론 한 문장으로 두게 하고, 사용자 지시는 압축한 소제목 대신 여러 줄 불릿으로 결론을 풀게 한다.

SKILL.md에서 `h2`를 목차 명사구로 정한 대목을 모두 이 체계에 맞게 고친다. 대상은 다음과 같다.

- 글쓰기 규칙 표의 `<title>`·`h1`·`h2` 행
- 페이지 구성의 순서 목록과 'TITLE-CLAIM보다 우선한다'는 문장
- 완료 기준의 '목차 읽기'와 '결론 읽기'
- 흔한 실수의 '라벨에 내용을 넣음'

페이지형 문서에서는 `.toc`와 `.sec`을 모아 목차로 읽고, 결론 제목을 모아 논지를 읽는다. 단일 문서의 규칙(명사구 절 제목과 결론 첫 문장)은 바꾸지 않는다.

내부 검토 문서에는 확인 상태와 원자료를 함께 쓴다.

- **확인 상태:** 결론 줄마다 `<span class="state" data-state="run|infer|assume">`로 표시한다. 글자(실행으로 확인함·추론함·가정함)는 마크업에 직접 쓴다. 외부 독자 문서에는 쓰지 않는다.
- **원자료 병기:** `run`(실행으로 확인함)은 같은 줄에 그 결론을 받치는 명령·출력·커밋·파일 줄이 있을 때만 쓴다. 원자료가 없는 결론은 `infer`나 `assume`이다.

한 페이지에서 결론 불릿·도식·표가 같은 사실을 반복하지 않는다. 도식은 표로 보이기 어려운 구조·흐름·동작을 보일 때만 둔다. 도식의 형태와 그리는 방법은 `시각화.md`가 정한다.

## 판정 1차 뒤 보강

L1 판정 1차(2026-10-04)에서 재생성 보고서의 체크리스트 content 충족률은 후보 37.5%, 기준선 25%였다. 이해도·심은 오류·제목 연결은 통과했다. 독자와 검토자가 후보 보고서에서 찾은 내용 결함을 막도록 다음을 넣는다.

- **실행 확인의 원자료:** `data-state="run"`은 같은 줄에 명령·시험 출력·커밋·`파일:줄`이 있을 때만 쓴다. 문서를 읽어서 안 내용은 원자료 위치를 밝히고 `infer`로 쓴다. 검사(`checks/content.py`)는 마무리 보고서에서 `run` 표시가 붙은 줄에 `<code>` 요소나 `파일:줄`·커밋 해시 형태의 원자료가 없으면 위반으로 낸다.
- **요약 줄의 근거 위치:** 머리말과 요약의 결론 줄마다, 같은 줄에 근거가 있는 절(절 이름이나 그 절로 가는 링크) 또는 원자료 위치를 적는다. 검사는 마무리 보고서의 요약 목록에서 확인 상태가 붙은 줄에 링크나 근거 표시가 없으면 위반으로 낸다. 정확한 판별 방식은 C3 L2가 정하고 `마무리-보고서.md`에 적는다.
- **건수 일치:** 머리말·요약·결정 요청 절이 같은 대상의 건수(정할 사항, 남은 일, 결함 수)를 말할 때 같은 수를 쓴다. 이 대조는 `마무리-보고서.md`의 완료 전 확인에 넣는다.
- **결정 요청의 범위:** 결정 요청 절에는 작업 결과에 대한 결정만 둔다. 보고서를 쓰는 절차(독자, 파일 분할, 요약 승인)의 결정은 작성 전에 받으며 보고서의 결정 요청에 넣지 않는다.
- **단정의 범위:** 실행하지 않은 결과를 단정하지 않는다(예: '중단 없이 진행된다'). 확인한 범위를 같은 줄에 밝힌다.

## 내용 검사

`checks/content.py`의 새 검사는 새 규약 문서에만 적용하고, 기존 규칙은 페이지 이름을 읽는 곳만 바꾼다.

**대조 방식.** 새 규칙 함수는 `(html, old_html)`을 받고 `RULES`에 원본 대조 방식 `old`로 등록한다. `old` 방식에서 check.py는 원본을 함수에 넘기기만 한다. 그래서 함수가 원본에도 같은 위반이 있으면 그 위반을 빼야 하고, 원본이 없으면(None) 모든 위반을 센다.

**새 규칙.** 다음 세 규칙을 추가한다.

- **약어 풀이:** 본문의 영문 약어가 풀이되어 있는지 검사한다. 약어는 대문자로만 된 2~6자 토큰이다. 풀이는 `.gloss` 목록의 용어, 또는 그 약어가 처음 나온 곳 바로 뒤의 괄호 풀이 중 하나다.
  - **제외 대상:** `code`·`pre`·`pre.mermaid`·`script`·`svg` 안의 글, 숫자가 섞인 토큰, 확장자가 붙은 파일 이름의 조각, 하이픈으로 이은 식별자의 조각
- **필수 절:** 마무리 보고서 표시가 있는 문서에서 다섯 `data-part`가 모두 있는지 검사한다.
- **원본 기준:** 마무리 보고서 표시가 있는 문서에서 머리에 `p.basis`가 있고, 그 안에 커밋 해시(7자 이상 16진수)·`.md` 경로·파일 경로 중 하나가 있는지 검사한다.

**페이지 이름 읽기.** `page_violations`와 `page_scores`가 페이지 이름을 `.sec`에서 읽게 바꾼다. `.sec`이 없으면 지금처럼 첫 `h2`에서 읽는다. 이 변경으로 기준 규칙과 판정이 갈리는 경우는 `.sec`이 있는 페이지의 결론 `h2`가 '요약·결론·부록'으로 시작할 때뿐이다. L1은 기준 규칙 검사(`--base-checks`)에서 이 경우의 `score_violations` 위반만 제외한다. 기존 규칙은 느슨하게 바꾸지 않는다.

## 견본

`examples/wrapup.html`은 마무리 보고서 표시, 다섯 필수 절, 원본 기준, 페이지 구성, 확인 상태와 원자료를 모두 갖춘 페이지형 견본이다. 내용은 가상의 작업이며, 가상이라고 밝힌다. `template-paged.html`을 복사해 만들고 `python build.py examples/wrapup.html`로 관리 블록을 채운다. C2가 만드는 클래스만 쓰고, 문서 전용 CSS로 새 화면 요소를 만들지 않는다. `SKILL.md`와 `마무리-보고서.md`는 이 견본을 가리킨다.

## 검증

L2는 아래 확인을 통과한 뒤 브랜치를 넘긴다. C2가 병합되기 전이라 이 워크트리에는 결론 제목 검사가 없다. 그래서 자가 점검에서는 현재 라벨 검사가 `.sec` 페이지의 결론 `h2`에 내는 '라벨이 명사구가 아님' 위반만 제외한다.

1. **규칙 검사:** `python check.py examples/wrapup.html`의 위반이 위 제외 대상뿐이다.
2. **기계 판정:** `python eval/gates.py examples/wrapup.html --only content`의 `rules-all` 실패 내역이 위 제외 대상뿐이다.
3. **고정 견본 오탐:** 새 규칙을 `bench/fixed/*.html`과 두 템플릿에 실행해 위반이 0건임을 확인하고, 규칙별 결과를 리포트에 적는다. 이 문서들은 새 규약 문서가 아니므로 새 규칙의 적용 대상이 아니다.
4. **단위 시험:** `python -B -m unittest discover -s tests`가 통과한다. 시험 대상은 아래와 같다.
   - **새 규칙:** 규칙마다 통과 입력, 위반 입력, 원본에 같은 위반이 있는 입력, 새 규약이 아닌 문서를 둔다.
   - **약어 제외 대상:** 제외 대상마다 입력을 둔다.
   - **페이지 이름 읽기:** `.sec`이 있는 문서와 없는 문서를 둔다.
5. **자가 점검:** `examples/wrapup.html`을 `eval/shoot.py`로 찍는다. 그 출력만 받은 서브에이전트가 체크리스트 `content` 항목(`titles-tell-story`, `no-triple-repeat`, `decision-recommend`, `claims-sourced`)을 검토한다. 한 차례는 검토 3회이고, 항목마다 다수결을 낸다. 충족률은 다수결이 '예'인 항목 수를 '해당 없음'이 아닌 항목 수로 나눈 값이며, 85% 이상이어야 한다. 이 차례는 3번까지 하고, 세 번째에도 기준에 못 미치면 리포트에 적고 작업을 끝낸다.

공식 판정은 L1이 C2를 병합한 뒤 C3 브랜치에 main을 받아 한다. 판정 방식은 상위 설계를 따른다. 재생성 원자료마다 보고서 2개를 만들고, 각 보고서에 이해도 시험과 체크리스트를 3회씩 실행한다. 기준은 다음과 같다.

- **이해도:** 고정 질문 정답률 100%, 추가 질문 1개 이하, 심어 둔 오류 3회 중 2회 이상 발견, 제목 연결 3회 중 2회 이상 일치
- **체크리스트:** `content` 항목 85% 이상
- **판정 규칙:** 하락 금지, 판정 차례 3번

그러므로 견본 하나에만 맞춘 규칙을 두지 않는다.
