# 보고서 품질 개선 아키텍처 설계

작성일 2026-10-04 · 대상 스킬 `writing-html-reports`

## 목적과 범위

이 설계는 보고서 품질 개선을 평가 하네스와 개발 컴포넌트 셋으로 나누고, 소유 파일과 인터페이스를 고정해 병렬 개발이 충돌하지 않게 한다. 실행 방식은 disciplined-coder `nested-orchestration` 스킬의 3층 병렬 실행이고, 이 문서는 아래 용어를 쓴다.

- **L1:** 메인 세션이다. 사용자와 대화한다. 판정·병합·통합의 최종 승인자다.
- **L2:** 컴포넌트를 하나씩 맡는 자율 서브오케스트레이터다. 사용자와 대화하지 못한다.
- **L3:** L2가 실행하는 구현자와 렌즈 서브에이전트다.
- **spec 잠금:** L1이 spec을 쓰고 렌즈 리뷰를 거쳐 확정하는 일이다. 잠긴 spec은 L2의 원본이 된다.
- **BLOCKED:** L2가 사용자 결정이나 소유권 밖 수정이 필요해 작업을 멈추고, 질문과 함께 L1에 돌려주는 상태다.
- **팬아웃:** L1이 여러 L2를 동시에 디스패치하는 단계다.
- **고정 견본:** 호출 코드까지 고정한 HTML 사본이다. 새 CSS·JS로 다시 빌드해 개선 전후를 비교한다.
- **보류 자료:** L1만 보관하는 평가 자료다. 정답이 든 질문, 심을 오류의 정의, 고정 견본에 없는 조건을 담은 보류 견본, 재생성용 원자료가 여기에 든다.

컴포넌트 spec은 L1이 이 설계를 원본으로 차례로 잠근다. 각 L2는 잠긴 spec으로 plan을 쓰고 독립 워크트리에서 구현한다.

개선 요구는 2026-10-04 세션 분석에서 나왔고, 근거 파일은 `docs/superpowers/research/2026-10-04-report-quality/`에 있다.

사용자 지적과 실측이 첫째 근거다. 분기 흐름도 애니메이션(`D:/projects/Structure/lens-groups-report/04-rules.html`의 `d-flow`)은 28단계 전체가 8.7~9.0초에 끝나, 단계마다 0.32초 머문다. 설명은 그림 아래 자막에만 나오고, 캐릭터와 설명 상자는 없다. 재생 버튼은 1단계 연출을 생략한다. 같은 측정에서 완료 판정 도구 `RC.check`는 이 문서를 통과시켰다. 측정 코드와 결과는 `measurement-04-rules.md`에 있다.

마무리 확인 대화가 둘째 근거다(`improvement-draft.md`). 보고서를 받은 뒤 사용자가 변경 전후 사례, 남은 항목, 미룬 보강을 따로 물었다. 원격 열람 요청은 두 세션에서 나왔다. 확정 전 spec으로 만든 보고서는 spec이 바뀐 뒤 낡았다.

셋째 근거는 선행연구 렌즈의 요지(`lens-prior-art-A~D.md`)와 시각 검토 기준선(`visual-review-baseline.md`)이다. 기준선에서 최근 산출물 네 개의 평균 점수는 2.6~3.2점이다. 척도는 L1이 시각 검토 서브에이전트에 준 1~5점 기준이다.

사용자가 정한 조건은 다음과 같다.

- **개발 구조:** 아키텍처는 L1이 정하고, 컴포넌트는 병렬로 개발한다.
- **재생 방식:** 애니메이션 엔진은 한 워크트리에서 자동 재생과 단계 넘김을 모두 구현한다. 기본값은 L1이 실측해 정하고, 실측으로 가려지지 않으면 사용자에게 묻는다.
- **비교 대상:** 엔진과 CSS는 고정 견본으로 측정한다. 내용 규격과 최종 통합은 고정 원자료로 보고서를 다시 만들어 측정한다.
- **완료 기준:** 아래 「완료 기준」 절의 권장 기준을 쓴다.
- **제목 체계:** 페이지형 보고서는 작은 절 이름(목차) 아래에 결론 한 문장 제목을 두고, 그 아래에 여러 줄 불릿으로 결론의 세부를 푼다. 사용자 원칙 `TITLE-LAYERS`(한 페이지씩 넘겨 보는 HTML은 슬라이드로 다룬다)와 2026-09-27 사용자 지시(압축한 소제목 대신 여러 줄 불릿)를 함께 따른다.
- **판정 권한:** L1이 최종 승인자다. 사용자에게는 되돌리기 어려운 작업, 외부 전송, 가치 판단만 묻는다.
- **도구:** 화면 판정은 Python Playwright 1.63.0의 헤드리스 Chromium으로 한다. L2마다 독립 브라우저를 띄워 병렬 작업이 서로 막지 않게 한다. 공유 브라우저인 Playwright MCP는 병렬 작업에 쓰지 않는다.

범위 밖은 다음과 같다.

- 설치본 갱신과 원격 push는 통합 뒤 사용자에게 묻는다.
- 인지 강제 장치(승인 전에 독자가 먼저 판단하게 하는 장치)는 이번에 넣지 않는다. 과의존은 줄이지만 만족도를 낮춘다는 연구 결과(`lens-prior-art-D.md`)가 있기 때문이다.

## 측정 체계

측정은 기계 판정, 이해도 시험, 이진 체크리스트의 순서로 하고, 앞 단계를 통과한 브랜치만 다음 단계를 측정한다. 평가자는 엔진의 자기 판정(`RC.check`)을 믿지 않고, DOM과 타임라인에서 직접 측정한다.

| 측정 | 측정 대상 | 측정 주체 | 점수 |
|---|---|---|---|
| 기계 판정 | 아래 문턱값 표의 항목과 check.py | `eval/gates.py`(헤드리스 Chromium) | 항목별 통과·실패 |
| 이해도 시험 | 고정 질문 정답률, 추가 질문 수, 심어 둔 오류 발견, 제목 연결 | 작업 내용을 모르는 서브에이전트 | 정답률·개수·발견 횟수 |
| 이진 체크리스트 | 범주별 예/아니오 항목 | 새 서브에이전트(같은 검토 3회의 다수결) | 충족률 |

체크리스트 범주는 사용자 만족도, 심미성, 구성, 이해 용이성, 논리 전개다. 각 항목에는 적용 대상 표시(`motion`·`layout`·`content`)를 붙여, 컴포넌트마다 해당 항목만 판정에 쓴다.

이해도 시험의 검토자는 스크린샷과 DOM 글만 받는다. 고정 질문은 사용자가 실제로 다시 물은 질문에서 만들고, 애니메이션 견본에는 그림이 보여 주는 과정을 묻는 그림 질문을 따로 둔다. 심어 둔 오류는 견본 사본에 틀린 수치나 근거 없는 결론 하나를 넣어 만든다. 제목 연결은 두 요약을 비교한다. 검토자가 절 이름과 결론 제목만 읽고 첫 요약을 쓰고, 전체를 읽고 둘째 요약을 쓴다. 판정자가 두 요약의 결론이 일치하는지 판정한다.

기계 판정의 문턱값은 L1이 정했다. 근거는 체류 시간에만 있다. 한국어 자막 업계 상한은 초당 12자인데, 흐름도는 도형과 글을 함께 봐야 하므로 초당 8자로 낮췄다. 도형 변화를 따라가는 시간으로 약 1초를 더했다(`lens-prior-art-A.md`). 그 밖의 값은 L1의 가정이며, C0 검증에서 실현 가능성을 확인한다.

| 판정 항목 | 문턱값 | 근거 |
|---|---|---|
| 자동 재생의 단계 체류 시간 | 1초 + n÷8초 이상, 그 값 + 3초 이하 | 자막 상한과 단계형 애니메이션 연구 |
| 단계 넘김의 단계 연출 | 0.4~2.5초, 누르기 전에는 다음 단계로 넘어가지 않음 | 가정 |
| 1단계 재생 | 처음 상태에서 재생이나 다음을 누르면 1단계 연출이 0.2초 이상 보임 | 가정 |
| 설명 상자 위치 | 현재 노드 경계에서 48px 이내이고 무대 요소와 겹치지 않음 | 가정 |
| 현재 노드 노출 | 단계가 바뀐 뒤 현재 노드와 설명 상자가 함께 화면 안에 있음 | 가정 |
| 글자 대비 | 본문 글자 4.5:1 이상, 막대·선·노드 테두리 3:1 이상 | WCAG 1.4.3·1.4.11 |
| 계열 색 구분 | 제2색각 모의 변환 뒤 계열 색 쌍의 CIE76 색차 15 이상 | 가정 |
| 390px 글자 | 보이는 글자(HTML·SVG) 11px 이상 | 가정 |
| 390px 넘침 | 문서 가로 넘침 없음. 넓은 표와 도식은 자기 스크롤 상자 안에서만 넘침 허용 | 가정 |
| 390px 표 열 | 스크롤 상자 밖 표의 셀 폭 56px 이상 | 가정 |
| 페이지 틀 | 페이지마다 보이는 페이지 번호 하나, 주소 끝 `#p2`로 이동하면 2페이지가 보임 | 기준선 결함 |
| check.py | 위반 0건 | 기존 규칙 |

문턱값 표의 용어 정의는 다음과 같다.

- **n:** 그 단계에서 화면에 새로 나타나는 모든 글의 글자 수다. 공백은 빼고 센다. 단계 문장, 설명 상자 글, 숫자 칸이 모두 들어간다.
- **무대 요소:** 애니메이션 SVG 안의 글자·도형·간선·간선 이름표다.
- **화면 안:** 1280×800 창에서 요소의 경계 상자가 창 안에 모두 들어온 상태다.
- **현재 노드:** `data-rc-active`가 붙은 요소다. 이 속성이 없는 엔진(개선 전 엔진)은 측정 불가로 보고 실패로 센다.

## 완료 기준

컴포넌트마다 적용하는 판정 항목과 견본이 다르고, 공식 측정은 L1이 병합 판정 직전에 한다. L2는 기계 판정과 체크리스트 자가 점검만 직접 실행한다. 자가 점검은 3회까지이고, 3회째에도 기준을 넘지 못하면 리포트에 적고 작업을 끝낸다.

| 대상 | 측정 견본 | 기계 판정 | 이해도 시험 | 체크리스트 |
|---|---|---|---|---|
| C1 애니메이션 엔진 | 고정 견본과 보류 견본의 애니메이션·도식·차트 | 체류 시간·단계 연출·1단계·설명 상자·현재 노드·390px SVG 글자·도식 넘침 | 그림 질문 정답률 100% | `motion` 항목 85% 이상 |
| C2 페이지 틀·CSS | 고정 견본 | 대비·계열 색·390px HTML 글자·넘침·표 열·페이지 틀·check.py 서식 규칙 | 적용하지 않음 | `layout` 항목 85% 이상 |
| C3 내용 규격 | 고정 원자료 재생성본(main의 엔진·CSS로 빌드) | check.py 전 규칙 | 아래 이해도 기준 전부 | `content` 항목 85% 이상 |
| 최종 통합 | 고정 원자료 재생성본과 고정 견본 | 문턱값 표 전부 | 아래 이해도 기준 전부 | 전 항목 85% 이상 |

C3와 최종 통합의 이해도 기준은 다음과 같다.

| 항목 | 기준 |
|---|---|
| 고정 질문 정답률 | 100% |
| 추가 질문 수 | 1개 이하 |
| 심어 둔 오류 발견 | 3회 중 2회 이상 |
| 제목 연결 | 3회 중 2회 이상 일치 |

재생성본은 원자료마다 2개를 만들고, 생성본마다 이해도 시험과 체크리스트를 3회씩 반복해 다수결을 낸다. 추가 질문 수는 3회의 중앙값을 쓴다. 모든 생성본이 기준을 넘어야 통과다.

모든 대상에는 하락 금지 규칙이 함께 적용된다. 기준선과 후보를 같은 방식으로 3회씩 반복 측정한다. 기준선 다수결이 '예'인데 후보 다수결이 '아니오'인 체크리스트 항목은 하락으로 센다. L1은 하락 항목의 원 출력을 직접 읽어 판정하고 근거를 판정 기록에 남긴다.

판정 차례는 컴포넌트마다 3번까지이고, 한 판정 차례 안에서 위 반복 측정을 한다. 세 번째 판정 차례에도 기준을 넘지 못하면 L1이 다시 디스패치할지 범위를 줄일지 정한다. 가치 판단이 걸리면 사용자에게 묻는다.

C1의 기본 재생 방식은 L1이 보류 견본에서 두 방식을 각각 측정해 정한다. 각 방식에는 그 방식의 기계 판정 항목만 적용한다. 그다음 그림 질문 정답률과 `motion` 체크리스트 충족률을 차례로 비교한다. 두 값이 모두 같으면 사용자에게 묻는다. 고른 기본값이 C1 브랜치의 기본값과 다르면, L1이 기본값 변경을 C1 재디스패치로 맡긴다.

## 컴포넌트와 소유 파일

팬아웃 뒤에는 파일마다 소유자가 하나다. 소유하지 않은 파일을 고쳐야 하는 L2는 BLOCKED로 L1에 올린다. 아래 「L1 사전 정리」는 팬아웃 전에 하므로 이 규칙의 적용을 받지 않는다.

| 담당 | 하는 일 | 소유 파일 |
|---|---|---|
| L1 | 사전 정리, 보류 자료 작성 지시, 공식 측정, 병합, 관리 블록 재빌드, 통합 | `check.py`, `checks/__init__.py`, `checks/common.py`, `build.py`, `글쓰기-규칙.md`, `금지어.md`, `.gitignore`, `assets/**`, `tests/test_common.py`, `tests/test_cli.py`, `tests/test_build.py`, 다른 소유자가 없는 `docs/**` |
| C0 평가 하네스 | 고정 견본, 측정 도구, 체크리스트, 기준선 | `eval/**`, `bench/**`, `tests/test_eval_*.py` |
| C1 애니메이션 엔진 | 아래 C1 목록 | `report-charts.js`, `report-demo.css`, `report-peeps.js`, `tools/build-peeps.py`, `checks/anim.py`, `시각화.md`, `tests/sample-anim.html`, `tests/sample-viz.html`, `tests/test_anim.py`, `tests/test_peeps.py` |
| C2 페이지 틀·CSS | 아래 C2 목록 | `report-base.css`, `template.html`, `template-paged.html`, `checks/style.py`, `보고서-규격.md`, `tests/test_style.py` |
| C3 내용 규격 | 아래 C3 목록 | `SKILL.md`, `checks/content.py`, `examples/**`, `tests/test_content.py` |

각 L2가 쓰는 plan과 리뷰 기록은 그 컴포넌트 소유다. 파일 이름에 컴포넌트 이름을 넣는다. 예: `docs/superpowers/plans/2026-10-05-c1-animation-engine.md`.

C1이 맡는 일은 다음과 같다.

- **재생:** 체류 시간, 1단계 수정, 자동 재생과 단계 넘김, 단계 이름 앞부분('시나리오 A · …')으로 시나리오 묶기를 구현한다.
- **설명과 강조:** Mermaid 노드 옆 설명 상자, 설명 이중화 제거(상자와 하단 자막이 같은 말 반복), 긴 흐름도의 현재·지나온 노드 강조와 화면 안 유지를 맡는다.
- **스틱맨:** 판단 노드의 판정 상태 표시에만 쓴다.
- **도식과 차트:** SVG 도식의 390px 글자, 차트 계열 직접 이름표와 선 표식, 손익 선 그래프 축, 전후 전환 끝 화면의 기준선 막대 유지를 맡는다.
- **규칙 문서:** `시각화.md`의 RC 함수 표와 시각화·애니메이션 규칙을 맡는다.

C2가 맡는 일은 다음과 같다.

- **색:** 색 토큰의 대비와 색각 구분을 맡는다.
- **배치:** 넓은 표의 모바일 배치, 용어 목록 배치, 페이지 번호 중복, 주소 끝 `#p2` 같은 페이지 앵커로 이동할 때의 페이지 전환을 맡는다.
- **제목 틀:** 절 이름 + 결론 제목 + 불릿의 페이지 머리 배치를 템플릿에 넣는다.
- **C3용 화면 요소:** 바뀐 칸 강조, 확인 상태 표시, 대체됨 배너의 클래스와 CSS를 만든다.

C3가 맡는 일은 다음과 같다.

- **마무리 보고서 필수 절:** 바뀐 것(전후 표와 바뀐 칸 강조), 처음 요청 대비 달성, 남은 일(항목마다 처분·권장안·예정 시점), 결정 요청(선택지·권장안·기각한 대안), 검증 범위(실행으로 확인한 것과 확인하지 않은 것)를 둔다.
- **결정 먼저:** 요약 결론 확인 단계에서 미결정 사항이 나오면 보고서를 쓰기 전에 하나씩 결정받는다. 결정한 사항은 기각한 대안과 함께 남긴다.
- **확인 상태와 원자료:** 내부 검토 문서의 결론 줄마다 확인 상태(실행으로 확인함·추론함·가정함)를 표시한다. 결론 옆에는 테스트 출력·커밋·파일 줄을 둔다.
- **원본 기준 표시:** 보고서가 어느 커밋·spec 기준인지 적는다. 원본이 바뀐 문서에는 대체됨(superseded) 배너를 단다.
- **제목 체계:** 위 「목적과 범위」의 제목 체계를 SKILL.md 페이지 구성 규칙으로 정한다.
- **질문과 용어 먼저:** 파일이 답하는 독자의 질문을 첫머리에 보이고, 핵심 용어는 애니메이션 재생 전에 풀이한다. 본문 약어를 추출해 용어 풀이 목록과 대조하는 검사를 둔다.
- **반복 금지:** 한 페이지에서 불릿·도식·표가 같은 사실을 반복하지 않도록 도식 삽입 조건을 둔다.
- **시각 검토 단계:** 완료 기준에 C0 하네스의 기계 판정과 시각 검토 서브에이전트 실행을 넣는다.
- **원격 게시:** 게시할 때마다 사용자 확인을 받고, 게시 전에 민감 정보를 점검한다.

C3는 C2가 만드는 클래스만 쓰고 문서 전용 CSS로 새 화면 요소를 만들지 않는다. SKILL.md에서 시각화·애니메이션·스타일 규칙은 `시각화.md`와 `보고서-규격.md`를 가리키는 문장만 둔다.

`examples/`는 C3가 새로 만드는 폴더다. 위 필수 절을 모두 갖춘 마무리 보고서 견본(`examples/wrapup.html`)을 둔다.

build.py가 채우는 관리 블록(css·js 사본)은 생성물이다. L2는 자기 소유 파일에만 build.py를 실행하고, L1이 병합할 때마다 모든 관리 블록을 다시 빌드한다.

## L1 사전 정리

L1은 팬아웃 전에 main에서 동작을 바꾸지 않는 구조 변경을 변경마다 따로 커밋하고, 커밋마다 시험 개수와 검사 출력이 변경 전과 같은지 확인한다. 이 정리가 끝나면 파일 단위 소유권이 겹치지 않는다.

**check.py 분할.** 규칙을 소유자별 모듈로 옮긴다.

- **`checks/style.py` (C2):** 서식(`style_violations`), 라벨(`label_violations`), 스크립트 주소·버전 고정·색 리터럴 규칙
- **`checks/content.py` (C3):** 페이지 근거(`page_violations`), 별 상한, 점수표(`page_scores`·`score_violations`)
- **`checks/anim.py` (C1):** 애니메이션 목록(`anim_violations`), 파일당 애니메이션 개수 상한, GSAP 직접 호출·차트 애니메이션·차트 장식 규칙
- **`checks/common.py` (L1):** 공통 파서, 공용 상수(`PAGE_ID`·`TOC`), 금지어 검사

`script_violations`는 규칙 이름 단위로 style과 anim에 나눈다. `star_violations`는 별 상한(별 표시 페이지 개수의 상한)과 애니메이션 개수 상한으로 나눈다.

`check.py`에는 집계기, 원본 대조 분기, `preservation`(원본 본문 숫자와 문장의 보존율 계산)이 남는다. 각 모듈은 `RULES` 목록에 규칙 함수와 원본 대조 방식을 짝지어 둔다. 대조 방식은 지금 `main()`이 함수마다 하는 처리를 그대로 옮긴 값이다(규칙 이름 접두어 대조, 문장 집합 대조, 원본이 있으면 결과 비움, 원본 전달). 함수의 기존 서명은 바꾸지 않는다.

**시험 분할.** `tests/test_check.py`를 `tests/test_common.py`·`tests/test_style.py`·`tests/test_content.py`·`tests/test_anim.py`·`tests/test_cli.py`로 나누고 원래 파일을 지운다. 명령줄로 check.py를 실행하는 시험(Templates·DemoCount·Original)은 `tests/test_cli.py`로 간다.

**SKILL.md 분할.** 「시각화」 절과 「애니메이션」 절을 `시각화.md`로 옮긴다. 「완료 기준」의 애니메이션 판정 문장도 `시각화.md`를 가리키게 고친다. 그 절을 가리키던 참조도 새 파일을 가리키게 고친다. 대상은 `보고서-규격.md`, check 주석, 목록 일치 시험(`ListSync`), `report-charts.js` 5행 주석, SKILL.md 103행 선택 표다.

**애니메이션 CSS 분리.** `report-base.css`의 `.demo-*` 규칙을 `report-demo.css`로 옮긴다. 대상은 110~117행과, `@media print` 블록 안의 179~180행이다. 인쇄용 규칙은 같은 매체 블록으로 감싸 옮긴다. `build.py`는 report-base 블록에 두 파일을 이어 넣는다.

**견본 소유.** `tests/sample-viz.html`은 차트·Mermaid 도식·'구조' 애니메이션 견본이므로 C1 소유로 둔다. 파일을 옮기지 않는 이유는 '구조' 애니메이션 두 개를 `tests/sample-anim.html`로 옮기면 파일당 애니메이션 상한(3개)과 별 표시 상한(3개)을 넘기 때문이다.

커밋마다 다음 확인을 실행한다.

- **시험:** `python -B -m unittest discover -s tests -v`가 분할 전과 같은 개수로 통과한다.
- **검사 출력:** 변경 전후 check.py를 같은 입력에 실행해 출력 원문을 비교하고, 차이가 없어야 한다. 입력은 저장소의 모든 HTML과 `lens-groups-report`의 HTML이다. 각 HTML을 단독으로 실행하고, `template.html`을 원본으로 한 두 인자 실행도 한다.
- **스타일:** 견본 페이지의 `.demo-*` 요소 계산 스타일을 화면 매체와 인쇄 매체에서 각각 비교하고, 분리 전후에 같아야 한다.

## 인터페이스

컴포넌트 사이의 계약은 아래 항목이고, 어느 컴포넌트도 이 계약을 깨지 않는다.

**RC 호출 호환.** RC는 `report-charts.js`가 내보내는 함수 묶음이다.

- **보존 대상:** `RC.demo(figure, [{name, text, play}])`, `RC.fx.*`, `RC.icon`, `RC.note`, `RC.focus`, `RC.check`, `RC.chart`의 기존 인자는 그대로 동작한다.
- **고정 호출 코드:** 고정 견본의 호출 코드를 바꾸지 않아도 개선이 나타나야 한다.
- **새 기능:** 선택 인자로만 더한다.

**재생 방식 전환.** 엔진은 페이지 주소의 `?rc-mode=auto` 또는 `?rc-mode=step`을 읽어 재생 방식을 바꾼다. 주소에 값이 없으면 엔진의 기본값을 쓴다. C0은 이 인자로 한 견본을 두 방식으로 측정한다.

**계측 지점.** C0은 엔진 안을 읽지 않고 아래 지점만 읽는다.

- figure의 `data-rc-ready="1"`과 `data-rc-mode`(`auto` 또는 `step`)
- `fig._rcTl`(GSAP 타임라인, 단계 끝 라벨 `e0`·`e1`…)
- 단계 목록 `.demo-steps li`
- 조작 버튼 `.demo-ctl button`(이전·재생·다음·처음부터 순서)
- 설명 상자 `.rc-note`, 아이콘 `.rc-icon`
- 현재 연출 중인 도형의 `data-rc-active`

`data-rc-mode`와 `data-rc-active`는 C1이 새로 단다.

**CSS 토큰.** C2는 토큰 값을 바꾸거나 새 토큰을 더할 수 있으나, 기존 토큰 이름을 지우지 않는다. C1의 차트 이름표와 계열 색은 토큰 이름으로만 색을 참조한다.

**check 모듈.** 각 모듈은 `RULES` 목록을 두고, 항목마다 규칙 함수와 원본 대조 방식을 짝짓는다. 새 규칙은 이 목록에 더하며, `check.py`는 고치지 않는다.

**평가 실행.** C0이 제공하는 명령은 다음과 같다.

- `python eval/gates.py <html>… [--mode auto|step] [--only motion|layout|content]`: 결과 JSON을 출력하고, 실패가 있으면 종료 코드 1을 돌려준다.
- `python eval/rebuild.py <출력 폴더>`: `bench/fixed/`의 견본을 출력 폴더에 복사한 뒤, 현재 워크트리의 CSS·JS로 빌드한다. `bench/`는 바꾸지 않는다.
- `python eval/shoot.py <html> <출력 폴더> [--mode auto|step]`: 1280·390 폭 페이지별 스크린샷과 애니메이션 단계별 장면을 만든다.

체크리스트는 `eval/checklist.md`, 검토 프롬프트 틀은 `eval/prompts/`에 둔다.

## 평가 자료의 격리

정답이 든 보류 자료는 L1만 알고 쓴다. 저장소에는 측정 도구, 체크리스트, 고정 견본만 둔다. 평가자와 피평가자를 나누기 위해서다.

- **보류 자료의 작성:** L1이 보류 자료 작성 서브에이전트를 따로 실행한다. 이 서브에이전트는 어느 워크트리에도 속하지 않고 저장소 밖 보류 폴더에만 쓴다. C0을 포함한 어느 L2도 보류 자료를 만들거나 읽지 않는다.
- **보류 폴더의 위치와 조건:** 보류 폴더 경로와 보류 견본의 조건은 이 문서와 컴포넌트 spec에 적지 않는다. L1의 메모리와 보류 자료 작성 서브에이전트의 프롬프트에만 둔다.
- **남는 위험:** L3가 파일 시스템을 뒤져 보류 폴더를 찾아 읽는 일은 기계로 막지 못한다. L1은 각 브랜치의 diff와 리포트에서 보류 자료의 문구가 보이면 해당 측정을 무효로 한다.
- **고정 견본:** `bench/fixed/`에 다음 파일의 사본을 둔다.
  - `D:/projects/Structure/lens-groups-report/04-rules.html`(Mermaid 애니메이션)
  - `D:/projects/Structure/lens-groups-report/session-report.html`(페이지형 마무리 보고서, 표·용어 목록·페이지 번호 포함)
  - 사전 정리 직후의 `tests/sample-anim.html`과 `tests/sample-viz.html`

  앞의 두 사본은 공개 플러그인(disciplined-coder)의 작업 내용이다. 원격 push 전에 L1이 공개해도 되는지 사용자에게 묻는다.
- **고정 원자료:** 재생성용 원자료는 보류 자료에 들고, 사내 프로젝트 내용이 있어 원격 저장소에 올리지 않는다.
- **재생성:** 생성자는 스킬 경로와 원자료만 받는 새 서브에이전트다. 개선 전 스킬은 사전 정리 직후 커밋의 별도 워크트리에서 쓴다. 생성과 측정은 L1이 실행한다.
- **기준선:** 고정 견본의 기준선은 사전 정리 직후 커밋에서 C0이 3회 측정해, `eval/baseline/`에 커밋 해시와 함께 고정한다. 재생성 기준선은 L1이 같은 커밋의 스킬로 만들어 보류 폴더에 둔다.

## 실행 순서

사전 정리와 C0을 차례로 끝낸 뒤 C1·C2·C3을 병렬로 실행하고, L1이 판정·병합·통합을 한다.

1. **사전 정리:** L1이 위 절의 구조 변경을 변경마다 커밋한다. 확인: 커밋마다 그 절의 시험·검사 출력·스타일 비교가 모두 같다.
2. **C0:** L1이 C0 spec을 잠그고, C0의 L2가 워크트리에서 plan을 쓰고 구현한 뒤 기준선을 측정한다. 확인: 다음 세 결과가 리포트에 있다.
   - `eval/gates.py`가 고정 견본에서 오늘 확인한 결함을 모두 실패로 잡는다. 결함은 단계당 0.32초, 1단계 생략, 설명 상자 없음, 390px의 SVG 글자 5~9px, 표 열 1~2글자 폭, 막대 대비 2.58:1이다.
   - 현재 엔진으로 만든 최소 견본(직접 그린 SVG 무대, 체류 시간과 설명 상자 배치를 지킨 것)이 애니메이션 문턱값을 모두 통과한다.
   - 체크리스트를 기준선에 3회 실행한 항목별 일치율과, 알려진 결함에 대응하는 항목이 기준선에서 '아니오'로 나오는지가 있다. 3회 중 2회 미만으로 일치하는 항목과 결함을 '예'로 판정한 항목은 문구를 고친 뒤 병합한다.
3. **보류 자료 작성:** C0 병합 뒤 L1이 보류 자료 작성 서브에이전트를 실행하고, 이해도 시험을 기준선에 3회 실행해 질문별 일치율을 기록한다. 확인: 정답이 기준선 보고서의 내용에서 도출되는지 L1이 표본 검토한다.
4. **C1·C2·C3:** L1이 C0 실행 중에 세 spec을 차례로 잠근다. C0 병합 직후의 main에서 워크트리를 만들어 동시에 디스패치한다. 확인: 각 L2의 리포트에 해당 기계 판정 전부 통과와 체크리스트 자가 점검 결과가 있다.
5. **공식 측정과 판정:** L1이 「완료 기준」 표대로 측정하고 병합 여부를 정한다. C1은 기본 재생 방식도 이때 정한다. 확인: 판정 기록에 대상별 점수, 하락 항목 판정, 기본 방식 선택 근거가 있다.
6. **통합:** L1이 아래 작업을 차례로 한다. 확인: 최종 통합 행의 기준을 모두 넘고 하락 항목이 없다.
   - 브랜치마다 변경 파일을 소유 파일 표의 경로와 대조하고, 브랜치 쌍마다 변경 파일의 교집합을 검사한다.
   - 추가된 plan마다 마지막 줄의 리뷰 마커(review-specs가 남기는 `spec-review` 주석)를 확인한다.
   - C2, C1, C3 순서로 병합하고 모든 관리 블록을 다시 빌드한다.
   - 최종 통합 기준으로 공식 측정을 하고, 최종 브랜치 리뷰를 실행한다.
7. **사용자 확인:** L1이 원격 push(고정 견본 사본의 공개 여부 포함)와 설치본 갱신을 묻는다. 확인: 설치본 폴더에서 `python -B -m unittest discover -s tests`가 통과한다.

설치본 갱신은 다음 순서로 한다. 기존 설치본(`~/.claude/skills/writing-html-reports`)을 skills 폴더 밖의 `~/.claude/skill-backups/writing-html-reports-<날짜>`로 옮긴다. 그다음 저장소 HEAD의 추적 파일만(`git archive`) 설치본 위치에 푼다. 문제가 생기면 백업 폴더를 원래 위치로 되돌린다.

## 함정과 주입 컨텍스트

각 L2에는 이번 세션에서 확인한 함정 가운데 자기 컴포넌트에 해당하는 항목을 넣는다. 같은 결함을 다시 찾는 비용을 막기 위해서다.

- **자기 판정의 맹점 (C0·C1):** `RC.check`는 겹침과 글 규칙만 보고, 체류 시간·1단계·설명 위치는 보지 않는다.
- **1단계 생략의 원인 (C1):** 시작할 때 `go(0, false)`가 타임라인을 `e0`으로 옮긴 뒤 재생해 1단계 연출이 빠진다(`report-charts.js` 430행).
- **체류 시간의 원인 (C1):** 머무는 시간은 무대 안 글 등장(`beats`)이 있을 때만 계산된다(`report-charts.js` 356~372행).
- **기존 상한의 한계 (C1):** 기존 상한 4초는 48자 넘는 문장에서 한국어 자막 상한(초당 12자)을 넘는다.
- **스틱맨의 용도 (C1):** 성인 독자에게 장식 캐릭터는 이해를 떨어뜨린다는 결과가 많다. 스틱맨은 판단 노드에서 판정 상태(고민, 통과·실패)를 알리는 데만 쓰고, 시나리오 첫 단계의 안내 스틱맨(`person-guide`)은 빼는 쪽을 기본으로 둔다.
- **설명 위치의 근거 (C1):** 그림과 설명을 가까이 두는 효과는 g = 0.63이다. g는 두 집단의 평균 차이를 표준편차로 나눈 효과 크기 지표다. 이 근거는 동적 그림과 좁은 화면 조건에서 약하다(`lens-prior-art-A.md`). 그래서 애니메이션과 390px 폭에서 설명 상자가 도형을 가리지 않는지 측정으로 확인한다.
- **설명 장치의 부작용 (C3):** 설명을 잘 보이게 할수록 틀린 결론의 승인도 늘어난다. 그래서 확인 상태 표시와 원자료 병기가 함께 들어가야 한다.
- **모바일 (C1·C2):** 390px 폭에서 SVG 글자가 5~9px로 줄고, 4열 이상 표가 1~2글자 폭으로 잘린다.

## 위험

가장 큰 위험은 LLM 판정이 실행마다 흔들려 판정이 뒤집히는 상황이다. 3회 다수결, 기준선 3회 측정, C0 단계의 항목 판별력 확인, 하락 항목의 L1 직접 판독으로 이 위험을 줄인다.

- **견본 과적합:** 보류 견본은 L1만 보관하고, C1 판정과 기본 방식 선택에 쓴다.
- **숫자 맞추기:** 가정으로 정한 문턱값은 C0 검증에서 실현 가능성을 확인하고, 체류 시간에는 상한을 둔다. 문턱값을 지키려고 겹침이나 가독성을 해치는 설계는 체크리스트에서 걸러진다.
- **호환 파손:** 고정 견본의 호출 코드를 바꿔야만 개선되는 설계가 필요하면 L2는 BLOCKED로 올린다.
- **비용:** 사소한 워크스트림 하나에 약 40k 토큰이 든다(`nested-orchestration` 스킬 「가드레일」의 실측값). 이번에는 L2 넷과 각자의 L3, 반복되는 서브에이전트 측정이 들어 그보다 몇 배 크다. 판정 차례 3번과 자가 점검 3회로 상한을 둔다.
