# 보고서 품질 개선 아키텍처 설계

작성일 2026-10-04 · 대상 스킬 `writing-html-reports` · 실행 방식 네스티드 오케스트레이션

## 목적과 범위

이 설계는 보고서 품질 개선을 평가 하네스 C0과 개발 컴포넌트 C1·C2·C3으로 나누고, 컴포넌트마다 소유 파일과 인터페이스를 고정해 병렬 개발이 충돌하지 않게 한다. 컴포넌트 spec은 L1이 이 설계를 원본으로 차례로 잠그고, 각 L2가 잠긴 spec으로 plan을 쓰고 독립 워크트리에서 구현한다.

이 문서가 쓰는 실행 용어는 다음과 같다.

- **네스티드 오케스트레이션:** 3층 병렬 실행 방식이다. 방법은 disciplined-coder의 `nested-orchestration` 스킬이 정한다.
- **L1:** 메인 세션이다. 사용자와 대화하고, spec을 잠그고, 판정·병합·통합을 맡는 최종 승인자다.
- **L2:** 컴포넌트마다 하나씩 두는 자율 서브오케스트레이터다. 사용자와 대화하지 못한다.
- **L3:** L2가 실행하는 구현자와 렌즈 서브에이전트다.
- **BLOCKED:** L2가 사용자 결정이나 소유권 밖 수정이 필요할 때 작업을 멈추고 L1에 질문과 함께 돌려주는 상태다.
- **팬아웃:** L1이 여러 L2를 동시에 디스패치하는 단계다.

개선 요구는 2026-10-04 세션 분석에서 나왔고, 근거 파일은 `docs/superpowers/research/2026-10-04-report-quality/`에 있다.

사용자 지적과 실측이 첫째 근거다. 분기 흐름도 애니메이션(`lens-groups-report/04-rules.html`의 `d-flow`)은 28단계 전체가 8.7~9.0초에 끝나 단계당 0.32초 머문다. 이 값은 L1이 Playwright MCP로 잰 타임라인 길이(8.96초)와 시각 검토 서브에이전트가 잰 재생 시간(8.7초)이다. 설명은 그림 아래 자막에만 나오고, 캐릭터와 설명 상자는 없다. 재생 버튼은 1단계 연출을 생략한다. 같은 측정에서 완료 판정 도구 `RC.check`는 이 문서에 `pass: true`를 돌려주었다.

마무리 확인 대화가 둘째 근거다(`improvement-draft.md`). 보고서를 받은 뒤 사용자가 변경 전후 사례, 남은 항목, 미룬 보강을 따로 물었다. 원격 열람 요청은 두 세션에서 나왔다. 확정 전 spec으로 만든 보고서는 spec이 바뀐 뒤 낡았다.

셋째 근거는 선행연구 렌즈의 요지(`lens-prior-art-A~D.md`)와 시각 검토 기준선(`visual-review-baseline.md`)이다. 기준선에서 최근 산출물의 평균 점수는 2.6~3.2점(5점 만점)이다.

사용자가 정한 조건은 다음과 같다.

- **개발 구조:** 아키텍처는 L1이 정하고 컴포넌트는 병렬로 개발한다. 애니메이션 엔진은 한 워크트리에서 자동 재생과 단계 넘김을 모두 구현한다. 기본값은 L1이 보류 견본으로 두 방식을 실측해 정한다.
- **비교 대상:** 엔진과 CSS는 호출 코드까지 고정한 견본 HTML을 새 엔진으로 다시 빌드해 측정한다. 내용 규격과 최종 통합은 고정 원자료로 보고서를 다시 만들어 측정한다.
- **완료 기준:** 아래 「완료 기준」 절의 권장 기준을 쓴다.
- **판정 권한:** L1이 최종 승인자로 판정한다. 사용자에게는 되돌리기 어려운 작업, 외부 전송, 가치 판단만 묻는다.
- **도구:** 화면 판정은 Python Playwright 1.63.0의 헤드리스 Chromium으로 한다. L2마다 독립 브라우저를 띄우므로 병렬 작업이 서로 막지 않는다. 공유 브라우저인 Playwright MCP는 병렬 작업에 쓰지 않는다.

범위 밖은 다음과 같다.

- 설치본(`~/.claude/skills/writing-html-reports`) 갱신과 원격 push는 통합 뒤 사용자에게 묻는다.
- 도표 결론을 단위 줄(`.u`)에 두는 규칙과 절 제목을 명사구로 두는 규칙은 사용자 원칙 `TITLE-LAYERS`에서 왔으므로 바꾸지 않는다.
- 인지 강제 장치(승인 전에 독자가 먼저 판단하게 하는 장치)는 과의존을 줄이지만 만족도를 낮춘다는 연구 결과(`lens-prior-art-D.md`)가 있어 이번에는 넣지 않는다.

## 측정 체계

측정은 기계 판정, 이해도 시험, 이진 체크리스트의 세 층으로 하고, 앞 층을 통과한 브랜치만 다음 층을 측정한다. 평가자는 엔진의 자기 판정(`RC.check`)을 믿지 않고 DOM과 타임라인에서 직접 측정한다.

| 층 | 측정 대상 | 측정 주체 | 점수 |
|---|---|---|---|
| 기계 판정 | 아래 문턱값 표의 항목과 check.py | `eval/gates.py`(헤드리스 Chromium) | 항목별 통과·실패 |
| 이해도 시험 | 고정 질문 정답률, 추가 질문 수, 심어 둔 오류 발견, 제목 연결 | 작업 내용을 모르는 새 서브에이전트 | 정답률·개수·발견 횟수 |
| 이진 체크리스트 | 사용자 만족도·심미성·구성·이해 용이성·논리 전개 아래 예/아니오 항목 | 새 서브에이전트(같은 검토 3회의 다수결) | 충족률 |

이해도 시험의 검토자는 스크린샷과 DOM 글만 받는다. 고정 질문은 사용자가 실제로 다시 물은 질문에서 만든다. 기본 질문은 "무엇이 바뀌었나", "남은 일과 그 처분은", "내가 결정할 것과 권장안은", "결론을 받치는 핵심 수치는"이다. 애니메이션 견본에는 그림이 보여 주는 과정을 묻는 그림 질문을 따로 둔다. 심어 둔 오류는 견본 사본에 틀린 수치나 근거 없는 결론 하나를 넣어 만든다. 제목 연결은 절 제목과 첫 문장만 읽고 쓴 요약을 전체 요약과 비교해 일치 여부를 판정한다.

기계 판정의 문턱값은 L1이 아래처럼 정한다. 한국어 자막 업계 상한은 초당 12자인데, 흐름도는 도형과 글을 함께 봐야 하므로 초당 8자로 낮췄다. 도형 변화를 따라가는 시간 1초도 더했다. 이 시간은 단계형 애니메이션 연구의 권장값이다(`lens-prior-art-A.md`).

| 판정 항목 | 문턱값 |
|---|---|
| 자동 재생의 단계 체류 시간 | 1초 + 그 단계 글자 수(공백 제외) ÷ 8초 이상 |
| 단계 넘김의 단계 연출 | 0.4~2.5초이고, 사용자가 누르기 전에는 다음 단계로 넘어가지 않음 |
| 1단계 재생 | 처음 상태에서 재생이나 다음을 누르면 1단계 연출이 0.2초 이상 보임 |
| 설명 상자 위치 | 현재 노드 경계에서 48px 이내이고 무대 요소와 겹치지 않음 |
| 현재 노드 노출 | 단계가 바뀐 뒤 현재 노드와 설명 상자가 함께 화면 안에 있음 |
| 글자 대비 | 본문 글자 4.5:1 이상, 막대·선·노드 테두리 3:1 이상 |
| 390px 폭 | 보이는 글자(HTML·SVG) 11px 이상, 문서 가로 넘침 없음(넓은 표는 자기 스크롤 상자 안에서만 허용) |
| check.py | 위반 0건 |

## 완료 기준

컴포넌트마다 적용하는 층과 견본이 다르고, 공식 측정은 L1이 병합 판정 직전에 한다. L2는 기계 판정과 체크리스트 자가 점검만 직접 실행하고, 이해도 시험과 공식 체크리스트는 실행하지 않는다.

| 대상 | 측정 견본 | 기계 판정 | 이해도 시험 | 체크리스트 |
|---|---|---|---|---|
| C1 애니메이션 엔진 | 고정 견본과 보류 견본의 애니메이션·도식 | 애니메이션·SVG 항목 전부 통과 | 그림 질문 정답률 100% | 애니메이션·도식 항목 충족률 85% 이상 |
| C2 페이지 틀·CSS | 고정 견본 | 대비·390px·check.py 서식 항목 전부 통과 | 적용하지 않음 | 심미성·배치 항목 충족률 85% 이상 |
| C3 내용 규격 | 고정 원자료 재생성본 | 전부 통과 | 아래 이해도 기준 전부 | 전 항목 충족률 85% 이상 |
| 최종 통합 | 고정 원자료 재생성본과 고정 견본 | 전부 통과 | 아래 이해도 기준 전부 | 전 항목 충족률 85% 이상 |

C3와 최종 통합의 이해도 기준은 다음과 같다.

| 항목 | 기준 |
|---|---|
| 고정 질문 정답률 | 100% |
| 추가 질문 수 | 1개 이하 |
| 심어 둔 오류 발견 | 3회 중 2회 이상 |
| 제목 연결 | 3회 중 2회 이상 일치 |

모든 대상에는 하락 금지 규칙이 함께 적용된다. 기준선과 후보를 각각 3회 측정한다. 기준선의 다수결이 '예'인데 후보의 다수결이 '아니오'인 체크리스트 항목을 하락으로 센다. 하락으로 표시된 항목은 L1이 원 출력을 직접 읽어 판정하고 근거를 판정 기록에 남긴다.

C1의 기본 재생 방식도 L1이 정한다. 보류 견본에서 두 방식의 그림 질문 정답률을 먼저 비교하고, 같으면 체크리스트 충족률로 정한다. 그래도 같으면 어느 방식인지 숨긴 쌍대 비교 3회의 다수결로 고른다.

공식 측정은 컴포넌트마다 3회까지 한다. 3회째에도 기준을 넘지 못하면 L1이 다시 디스패치할지 범위를 줄일지 정하고, 가치 판단이 걸리면 사용자에게 묻는다.

## 컴포넌트와 소유 파일

팬아웃 뒤에는 파일마다 소유자가 하나이고, 소유하지 않은 파일을 고쳐야 하는 L2는 BLOCKED로 L1에 올린다. 아래 「L1 사전 정리」는 팬아웃 전에 하므로 이 규칙의 적용을 받지 않는다.

| 담당 | 하는 일 | 소유 파일 |
|---|---|---|
| L1 | 사전 정리, 병합, 관리 블록 재빌드, 통합 | `check.py`(집계기와 원본 대조), `checks/common.py`(공통 파서와 금지어 검사), `build.py`, `글쓰기-규칙.md`, `금지어.md`, `tests/test_common.py`, `tests/test_build.py` |
| C0 평가 하네스 | 고정 견본, 보류 견본·질문·원자료, 측정 도구, 기준선 | `eval/**`, `bench/**`, `tests/test_eval_*.py`, 저장소 밖 보류 폴더 |
| C1 애니메이션 엔진 | 체류 시간, 1단계 수정, 노드 옆 설명 상자, 판정 스틱맨, 단계 넘김과 시나리오 분할, 긴 흐름도의 현재·지나온 노드 강조와 화면 안 유지, SVG 도식의 390px 글자, 차트 계열 직접 이름표와 선 표식 | `report-charts.js`, `report-demo.css`, `report-peeps.js`, `tools/build-peeps.py`, `checks/anim.py`, `애니메이션.md`, `tests/sample-anim.html`, `tests/test_anim.py`, `tests/test_peeps.py` |
| C2 페이지 틀·CSS | 색 토큰의 대비와 색각 구분, 넓은 표의 모바일 배치, 용어 목록 배치, 페이지 번호 중복, 주소 끝 `#p2` 같은 페이지 앵커로 이동할 때의 페이지 전환 | `report-base.css`, `template.html`, `template-paged.html`, `checks/style.py`, `보고서-규격.md`, `tests/sample-viz.html`, `tests/test_style.py` |
| C3 내용 규격 | 아래 목록의 내용 규칙과 그 검사, 마무리 보고서 견본 | `SKILL.md`, `checks/content.py`, `examples/**`, `tests/test_content.py` |

C3가 맡는 내용 규칙은 다음과 같다.

- **마무리 보고서 필수 절:** 바뀐 것(전후 표와 바뀐 칸 강조), 처음 요청 대비 달성, 남은 일(항목마다 처분·권장안·예정 시점), 결정 요청(선택지·권장안·기각한 대안), 검증 범위(실행으로 확인한 것과 확인하지 않은 것)를 둔다.
- **결정 먼저:** 요약 결론 확인 단계에서 미결정 사항이 나오면 보고서를 쓰기 전에 하나씩 결정받는다. 결정한 사항은 기각한 대안과 함께 남긴다.
- **확인 상태와 원자료:** 내부 검토 문서의 결론 줄마다 확인 상태(실행으로 확인함·추론함·가정함)를 표시하고, 결론 옆에 테스트 출력·커밋·파일 줄을 둔다.
- **원본 기준 표시:** 보고서가 어느 커밋·spec 기준인지 적고, 원본이 바뀐 문서에는 '대체됨(superseded)' 배너를 단다.
- **질문과 용어 먼저:** 파일이 답하는 독자의 질문을 첫머리에 보이고, 핵심 용어는 애니메이션 재생 전에 풀이한다. 본문 약어를 추출해 용어 풀이 목록과 대조하는 검사를 둔다.
- **반복 금지:** 한 페이지에서 불릿·도식·표가 같은 사실을 반복하지 않게 하는 도식 삽입 조건을 둔다.
- **시각 검토 단계:** 완료 기준에 C0 하네스의 기계 판정과 시각 검토 서브에이전트 실행을 넣는다.
- **원격 게시:** 게시할 때마다 사용자 확인을 받고, 게시 전에 민감 정보를 점검하는 절차를 둔다.

`examples/`는 C3가 새로 만드는 폴더다. 위 필수 절을 모두 갖춘 마무리 보고서 견본(`examples/wrapup.html`)을 둔다.

build.py가 채우는 관리 블록(css·js 사본)은 생성물이다. L2는 자기 소유 파일에만 build.py를 실행하고, L1이 병합할 때마다 모든 관리 블록을 다시 빌드한다. 템플릿의 애니메이션 견본은 기존 호출 코드를 그대로 쓰므로, C1 병합 뒤에는 재빌드만 하면 개선이 반영된다.

## L1 사전 정리

L1은 팬아웃 전에 main에서 동작을 바꾸지 않는 구조 변경을 하고, 시험 개수와 검사 출력이 변경 전과 같은지 확인한다. 이 정리로 파일 단위 소유권이 겹치지 않게 된다.

- **check.py 분할:** 규칙 함수를 소유자별 모듈로 옮긴다. 서식·라벨·스크립트 주소는 `checks/style.py`로, 페이지 근거·별 상한·점수표·`data-src`는 `checks/content.py`로 간다. 애니메이션 목록·개수·견본 상태는 `checks/anim.py`로 간다. `star_violations`는 별 상한과 애니메이션 개수 상한으로 나눠 각 모듈에 둔다. 공통 파서와 금지어 검사는 `checks/common.py`에 둔다. `check.py`에는 모듈별 `RULES` 목록을 실행하는 집계기, 원본 대조 분기, `preservation`이 남는다.
- **시험 분할:** `tests/test_check.py`를 모듈 단위로 나눈다. 결과 파일은 `tests/test_common.py`·`tests/test_style.py`·`tests/test_content.py`·`tests/test_anim.py`이고, 시험은 옮긴 함수를 새 모듈에서 부른다.
- **SKILL.md 분할:** 「애니메이션」 절을 `애니메이션.md`로 옮기고, SKILL.md에는 그 파일을 가리키는 문단만 남긴다. 그 절을 가리키던 `보고서-규격.md`와 check 주석, 목록 일치 시험(`ListSync`)도 새 파일을 가리키게 고친다.
- **애니메이션 CSS 분리:** `report-base.css`의 `.demo-*` 규칙(110~117행과 인쇄용 179~180행)을 `report-demo.css`로 옮긴다. `build.py`는 report-base 블록에 두 파일을 이어 넣는다.
- **견본 이동:** `tests/sample-viz.html`의 '구조' 애니메이션 두 개(`d-order`, `d-mmd`)를 `tests/sample-anim.html`로 옮기고, `애니메이션.md`의 견본 위치를 고친다.

확인 방법은 세 가지다.

- **시험:** `python -B -m unittest discover -s tests -v`가 분할 전과 같은 개수로 통과한다.
- **검사 출력:** 분할 전후의 check.py를 저장소의 모든 HTML과 `lens-groups-report`의 HTML에 실행해 출력 원문을 비교하고, 차이가 없어야 한다.
- **스타일:** 견본 페이지의 `.demo-*` 요소 계산 스타일이 분리 전후에 같다.

## 인터페이스

컴포넌트 사이의 계약은 아래 항목이고, 어느 컴포넌트도 이 계약을 깨지 않는다.

- **RC 호출 호환:** RC는 `report-charts.js`가 내보내는 함수 묶음이다. 기존 인자는 그대로 동작해야 한다. 대상은 `RC.demo(figure, [{name, text, play}])`, `RC.fx.*`, `RC.icon`, `RC.note`, `RC.focus`, `RC.check`, `RC.chart`다. 고정 견본의 호출 코드를 바꾸지 않아도 개선이 나타나야 한다. 단계 문장으로 머무는 시간을 정하는 일, Mermaid 노드 옆에 설명 상자를 자동으로 두는 일, 단계 이름 앞부분('시나리오 A · …')으로 시나리오를 묶는 일이 그 예다. 새 기능은 선택 인자로만 더한다.
- **계측 지점:** C0은 엔진 안을 읽지 않고 아래 지점만 읽는다.
  - figure의 `data-rc-ready="1"`
  - `fig._rcTl`(GSAP 타임라인, 단계 끝 라벨 `e0`·`e1`…)
  - 단계 목록 `.demo-steps li`
  - 조작 버튼 `.demo-ctl button`(이전·재생·다음·처음부터 순서)
  - 설명 상자 `.rc-note`, 아이콘 `.rc-icon`
  - 현재 연출 중인 도형의 `data-rc-active` 속성(C1이 새로 단다)
  - figure의 `data-rc-mode`(`auto` 또는 `step`, C1이 새로 단다)
- **CSS 토큰:** C2는 토큰 값을 바꾸거나 새 토큰을 더할 수 있으나, 기존 토큰 이름을 지우지 않는다. C1의 차트 이름표와 계열 색은 토큰 이름으로만 색을 참조한다.
- **check 모듈:** 각 모듈은 `RULES = [함수, …]`를 둔다. 함수는 `(html, old_html)`을 받아 위반 문장 목록을 돌려준다.
- **평가 실행:** C0이 제공하는 명령은 다음과 같다.
  - `python eval/gates.py <html>…`: 결과 JSON을 출력하고, 실패가 있으면 종료 코드 1을 돌려준다.
  - `python eval/rebuild.py <출력 폴더>`: `bench/fixed/`의 견본을 출력 폴더에 복사한 뒤, 현재 워크트리의 CSS·JS로 빌드한다. `bench/`는 바꾸지 않는다.
  - `python eval/shoot.py <html> <출력 폴더>`: 1280·390 폭 페이지별 스크린샷과 애니메이션 단계별 장면을 만든다.
  - 체크리스트는 `eval/checklist.md`, 검토 프롬프트는 `eval/prompts/`에 둔다.

## 평가 자료의 격리

평가자와 피평가자를 나누기 위해, 정답이 들어 있는 평가 자료는 저장소 밖 보류 폴더에 두고 L1만 쓴다. 체크리스트와 측정 도구는 설계 규칙의 일부이므로 저장소에 둔다.

- **보류 폴더:** `D:/projects/Structure/report-quality-holdout/`이다. C0이 만들고, 다른 L2의 프롬프트에는 이 경로를 넣지 않으며 읽지 말라고 적는다.
- **보류 폴더의 내용:** 고정 질문과 정답, 심을 오류의 정의, 보류 견본, 고정 원자료가 들어간다. 보류 견본은 고정 견본에 없는 조건을 담는다. 48자 넘는 단계 문장, 시나리오가 여럿인 흐름도, 직접 그린 SVG 무대가 그 예다. 고정 원자료는 렌즈 그룹 spec과 세션 기록, quant 시도 검토 자료다. 사내 프로젝트 내용이 들어 있으므로 원격 저장소에 올리지 않는다.
- **고정 견본:** `bench/fixed/`에 다음 네 파일의 사본을 둔다. `lens-groups-report/04-rules.html`(Mermaid 애니메이션), `lens-groups-report/session-report.html`(페이지형 마무리 보고서, 표·용어 목록·페이지 번호 포함), `tests/sample-anim.html`, `tests/sample-viz.html`이다. 뒤의 두 파일은 사전 정리 직후의 사본이다.
- **재생성:** 생성자는 스킬 경로와 원자료만 받는 새 서브에이전트이고, 원자료마다 스킬 버전마다 2회 생성한다. 개선 전 스킬은 사전 정리 직후 커밋의 별도 워크트리에서 쓴다. 생성과 측정은 L1이 실행한다.
- **기준선:** 고정 견본의 기준선은 사전 정리 직후 커밋에서 C0이 3회 측정해 `eval/baseline/`에 커밋 해시와 함께 고정한다. 재생성 기준선은 L1이 같은 커밋의 스킬로 만들어 보류 폴더에 둔다.

## 실행 순서

사전 정리와 C0을 차례로 끝낸 뒤 C1·C2·C3을 병렬로 실행하고, L1이 판정·병합·통합을 한다.

1. **사전 정리:** L1이 위 절의 구조 변경을 main에 커밋한다. 확인 방법은 그 절의 세 가지다.
2. **C0:** L1이 C0 spec을 잠그고, L2가 워크트리에서 plan을 쓰고 구현한 뒤 기준선을 측정한다. 확인 기준은 두 가지다. 첫째, `eval/gates.py`가 고정 견본에서 오늘 확인한 결함을 모두 실패로 잡아야 한다(단계당 0.32초, 1단계 생략, 설명 상자 없음, 390px의 SVG 글자 5~9px, 표 잘림, 막대 대비 2.58:1). 둘째, 이해도 시험과 체크리스트를 기준선에 3회 실행해 항목별 일치율을 기록한다. 3회 중 2회 미만으로 일치하는 체크리스트 항목은 문구를 고친 뒤 병합한다.
3. **C1·C2·C3:** L1이 C0 실행 중에 세 spec을 차례로 잠근다. C0 병합 직후의 main에서 워크트리를 만들어 동시에 디스패치한다. 확인: 각 L2의 리포트에 기계 판정 전부 통과와 체크리스트 자가 점검 결과가 있다.
4. **공식 측정과 판정:** L1이 「완료 기준」 표대로 측정하고 병합 여부를 정한다. C1은 기본 재생 방식도 이때 정한다. 확인: 판정 기록에 대상별 점수, 하락 항목 판정, 기본 방식 선택 근거가 있다.
5. **통합:** L1이 아래 작업을 차례로 한다.
   - 브랜치 쌍마다 변경 파일의 교집합을 검사한다.
   - 추가된 plan마다 마지막 줄의 리뷰 마커를 확인한다.
   - C2, C1, C3 순서로 병합한다.
   - 모든 관리 블록을 다시 빌드한다.
   - 최종 통합 기준으로 공식 측정을 하고, 최종 브랜치 리뷰를 실행한다.

   확인: 최종 통합 행의 기준을 모두 넘고 하락 항목이 없다.
6. **사용자 확인:** L1이 설치본 갱신과 원격 push를 묻는다. 설치본은 기존 폴더를 날짜를 붙인 백업 폴더로 옮긴 뒤 저장소 사본으로 통째로 바꾼다. 문제가 생기면 백업 폴더로 되돌린다. 확인: 설치본 폴더에서 `python -B -m unittest discover -s tests`가 통과한다.

## 함정과 주입 컨텍스트

각 L2에는 이번 세션에서 확인한 함정 가운데 자기 컴포넌트에 해당하는 것을 넣어, 같은 결함을 다시 찾는 비용을 막는다.

- **자기 판정의 맹점 (C0·C1):** `RC.check`는 겹침과 글 규칙만 보고, 체류 시간·1단계·설명 위치는 보지 않는다.
- **1단계 생략의 원인 (C1):** 시작할 때 `go(0, false)`가 타임라인을 `e0`으로 옮긴 뒤 재생해 1단계 연출이 빠진다(`report-charts.js` 430행).
- **체류 시간의 원인 (C1):** 머무는 시간은 무대 안 글 등장(`beats`)이 있을 때만 계산된다(`report-charts.js` 356~372행). 기존 상한 4초는 48자 넘는 문장에서 한국어 자막 상한(초당 12자)을 넘는다.
- **스틱맨의 용도 (C1):** 성인 독자에게 장식 캐릭터는 이해를 떨어뜨린다는 결과가 많다. 그래서 스틱맨은 판단 노드에서 판정 상태(고민 → 통과·실패)를 알리는 데만 쓴다. 기존의 안내 스틱맨(`person-guide`)은 시나리오 첫 단계에서 빼거나 줄이는 쪽을 기본으로 둔다.
- **설명 위치의 근거 (C1):** 설명을 도형 옆에 두는 개선의 효과 크기는 g = 0.63이다. g는 두 집단의 평균 차이를 표준편차로 나눈 효과 크기 지표이고, 0.5 이상이면 중간 이상으로 본다. 다만 좁은 화면 조건의 근거는 약하므로 390px 폭에서 설명 상자가 도형을 가리지 않는지 확인한다.
- **설명 장치의 부작용 (C3):** 설명을 잘 보이게 할수록 틀린 결론의 승인도 늘어난다. 그래서 확인 상태 표시와 원자료 병기가 함께 들어가야 한다.
- **모바일 (C1·C2):** 390px 폭에서 SVG 글자가 5~9px로 줄고, 4열 이상 표가 1~2글자 폭으로 잘린다.

## 위험

가장 큰 위험은 LLM 판정이 실행마다 흔들려 판정이 뒤집히는 상황이다. 3회 다수결, 기준선 3회 측정, 하락 항목의 L1 직접 판독으로 이 위험을 줄인다.

- **판정 흔들림:** C0 단계에서 항목별 일치율을 먼저 재고, 흔들리는 항목은 문구를 고친 뒤 쓴다.
- **견본 과적합:** 보류 견본은 L1만 보관하고, C1 판정과 기본 방식 선택에 쓴다.
- **호환 파손:** 고정 견본의 호출 코드를 바꿔야만 개선되는 설계가 필요하면 L2는 BLOCKED로 올린다.
- **보류 자료 노출:** 보류 폴더는 저장소 밖에 두지만, L2가 경로를 찾아 읽는 것을 기계로 막지는 못한다. 프롬프트로 금지하고, 리포트에서 그 경로를 읽은 흔적이 보이면 해당 측정을 무효로 한다.
- **비용:** 사소한 워크스트림 하나에 약 40k 토큰이 든다(`nested-orchestration` 스킬 「가드레일」의 실측값). 이번에는 L2 넷과 각자의 L3, 반복되는 서브에이전트 측정이 들어 그보다 몇 배 크다. 공식 측정을 컴포넌트마다 3회로 제한해 상한을 둔다.
